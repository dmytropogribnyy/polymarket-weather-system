# Ответ на внешнюю ревизию (2026-08-02)

Система прошла внешнюю ревизию (GPT, по просьбе владельца). Этот документ —
отчёт о проверке её утверждений на живых данных и о том, что было изменено.
Вердикт ревизии «NO-GO по текущим вероятностям» был принят: новые входы были
остановлены до завершения перестройки, описанной ниже.

## Проверка главных утверждений ревизии

**1. «Калибровка мерила не тот прогноз» — ПОДТВЕРЖДЕНО, главная находка.**
Historical-Forecast API склеивает ряды из первых часов последовательных
запусков (горизонт 0–6 ч), а торговля идёт на горизонте 24–48 ч. Проверка
через Previous Runs API (`temperature_2m_previous_day1/2`):

| Город | std по старой калибровке (0–6ч) | std на суточном горизонте |
|---|---|---|
| Мюнхен | 0.46 (тир A) | 1.11 |
| Сан-Франциско | 0.73 (тир A) | 0.65 |
| Чэнду | 1.20 (тир B) | 1.81 |

И критично: поправки семейств расходятся. Мюнхен: ECMWF +2.3°, GFS +2.2°,
ICON +0.3°, GEM +0.7° — а система прибавляла +2.5° всем 143 членам. Это
главный кандидат в объяснение промаха 2 августа (модель дала 32°C 35–40%,
факт 30°C). После честной пересборки тир A остаётся у ~4–7 городов из 48.

**2. «Комиссии игнорируются» — ПОДТВЕРЖДЕНО с точностью до 4-го знака.**
Сверка формулы `fee = 0.05·цена·(1−цена)` с акции по реальным сделкам
владельца: покупка 8.06 акций по 62¢ — списано $5.0950, модель комиссии
даёт ровно +$0.0950. На ноге в 2¢ комиссия ≈ +4.9% к цене. В сделках марта
2026 комиссий ещё не было — введены недавно, поэтому система о них не знала.

**3. «Chengdu резолвится по Wunderground, а не по NOAA» — ПОДТВЕРЖДЕНО.**
В описании рынка прямо указан Wunderground (страница станции ZUUU). METAR —
прокси; обычно это те же наблюдения той же станции, но контроль нужен.

**Замечания, отклонённые как «так задумано»:** пустой `PM_WALLET` в публичном
репозитории (адрес владельца намеренно живёт только в приватном тексте
scheduled-задачи); вырезанный код в `docs/tasks/` (код лежит в `src/`,
дублирование убрано сознательно). Замечания про формулировку «станция
извлекается из описания» и про отсутствие общего дневного распределителя
бюджета в коде — приняты, см. ниже.

## Что изменено (реализовано и стоит в продакшене)

1. **Калибровка v2** (`calibrate`): Previous Runs API, горизонты 1 и 2 суток
   раздельно, отдельные bias/std/SE **каждому семейству моделей**
   (примечание: GFS в Previous Runs живёт под именем `gfs_global`).
   Тиры: A — худшее семейство std ≤ 0.9 при n ≥ 6; B — std ≤ 1.5 при n ≥ 4;
   C — не торгуется.
2. **Вероятность v2** (`fam_prob`): равный вес каждому семейству (не по числу
   членов); каждому члену — поправка его семейства; ядро
   `τ_f² = max(0.36, std_f² − S²)`, где S² — разброс сегодняшнего ансамбля
   семейства — остаточная неопределённость без двойного счёта (ответ на
   вопрос №1). Стресс — сдвиг поправки каждого семейства на ±SE = std/√n
   (не на std: это была ошибка смешения дисперсии дня с неопределённостью
   среднего).
3. **Усадка к рынку** (вопрос №3): нормализованный лог-пул по бакетам события
   `p*_j ∝ p_j^λ · q_j^(1−λ)`, λ = 0.25 (вес модели) на фазе валидации,
   q — нормализованные середины рынка. Все решения (фильтры, EV, Келли) —
   по p*; сырая p_model сохраняется в отчёте для будущей проверки калибровки.
4. **Комиссии везде**: полная цена `c = a + 0.05·a·(1−a)` в фильтрах, EV,
   Келли, комбо, обходе стакана (`combo_lots`), обоих арбитражных детекторах
   (чистый арбитраж теперь только при сумме ПОЛНЫХ цен < 0.995; связка
   страйков — при полной цене < 0.99).
5. **Запрет дешёвых хвостов** (вопрос №9): ноги дешевле 3¢ исключены из
   комбо и одиночных входов до конца фазы валидации.
6. **Бюджет в коде** (вопрос №7): $15/день общий, **$5/день суммарно на все
   погодные входы одной даты** — считается от реальных покупок по кошельку
   (activity API), вердикты урезаются в коде, не в инструкциях.
7. **Fail-closed контроль резолюции** (вопрос №8): рынок отбрасывается, если
   единицы (°C/°F) не совпадают с моделью или источник резолюции не из
   списка Wunderground/NOAA/NWS. Отброшенные рынки перечисляются в отчёте
   (`res_checks`).
8. **Пересчёт комбо после исполнения** (вопрос №6, частично): `combo_lots`
   возвращает `ev_final` — EV набора после отсева ног и с комиссиями;
   комбо с `ev_final < 0.10` не рекомендуется.

## Принято к сведению, отложено (с причиной)

* **EMOS / оптимизация λ по log-score** — требует истории прогнозов, которая
  только начала накапливаться (система теперь пишет p_model и p* каждого
  бакета ежедневно). Вернёмся после ~2–3 недель данных.
* **Полный перебор подмножеств комбо с максимизацией log-роста** — отложен:
  при нынешних размерах ставок ($1–5) разница с жадным набором после
  пересчёта `ev_final` мала; вернёмся при росте лимитов.
* **Метрики RPS/log-loss по city-day** (вопрос №4) — план: единица
  наблюдения — city-day, не нога; Poisson-binomial тест для хвостовых
  наборов. Реализация после накопления выборки.
* **Архив разности Wunderground−METAR** (вопрос №2/№8) — Wunderground не
  отдаёт данные без ключа/скрейпинга; METAR остаётся прокси, риск признан
  и задокументирован.

## Статус после перестройки

Оба scheduled-задания обновлены и сверены с кодом побайтово. Первый полный
прогон v2: 48 городов, 0 ошибок; тиры A/B/C = 4/14/30; сигналов дня — ноль по
всем категориям, вердикты «пропуск». Это ожидаемое поведение: по новой
математике вчерашние сетапы не существовали. Пропуск дня — норма фазы
валидации.
