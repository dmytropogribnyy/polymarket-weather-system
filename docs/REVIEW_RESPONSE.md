# Ответ на внешнюю ревизию (2026-08-02)

Система прошла внешнюю ревизию (GPT, по просьбе владельца). Этот документ —
отчёт о проверке её утверждений на живых данных и о том, что было изменено.
Вердикт ревизии «NO-GO по текущим вероятностям» был принят: новые входы были
остановлены до завершения перестройки, описанной ниже.

## Проверка главных утверждений ревизии

**1. «Калибровка мерила не тот прогноз» — ПОДТВЕРЖДЕНО, главная находка.**
Historical-Forecast API склеивает ряды из первых часов последовательных
запусков (горизонт 0–6 ч), а торговля идёт на горизонте 24–48 ч. Проверка
через Previous Runs API (`temperature_2m_previous_day1/2`):

| Город | std по старой калибровке (0–6ч) | std на суточном горизонте |
|---|---|---|
| Мюнхен | 0.46 (тир A) | 1.11 |
| Сан-Франциско | 0.73 (тир A) | 0.65 |
| Чэнду | 1.20 (тир B) | 1.81 |

И критично: поправки семейств расходятся. Мюнхен: ECMWF +2.3°, GFS +2.2°,
ICON +0.3°, GEM +0.7° — а система прибавляла +2.5° всем 143 членам. Это
главный кандидат в объяснение промаха 2 августа (модель дала 32°C 35–40%,
факт 30°C). После честной пересборки тир A остаётся у ~4–7 городов из 48.

**2. «Комиссии игнорируются» — ПОДТВЕРЖДЕНО с точностью до 4-го знака.**
Сверка формулы `fee = 0.05·цена·(1−цена)` с акции по реальным сделкам
владельца: покупка 8.06 акций по 62¢ — списано $5.0950, модель комиссии
даёт ровно +$0.0950. На ноге в 2¢ комиссия ≈ +4.9% к цене. В сделках марта
2026 комиссий ещё не было — введены недавно, поэтому система о них не знала.

**3. «Chengdu резолвится по Wunderground, а не по NOAA» — ПОДТВЕРЖДЕНО.**
В описании рынка прямо указан Wunderground (страница станции ZUUU). METAR —
прокси; обычно это те же наблюдения той же станции, но контроль нужен.

**Замечания, отклонённые как «так задумано»:** пустой `PM_WALLET` в публичном
репозитории (адрес владельца намеренно живёт только в приватном тексте
scheduled-задачи); вырезанный код в `docs/tasks/` (код лежит в `src/`,
дублирование убрано сознательно). Замечания про формулировку «станция
извлекается из описания» и про отсутствие общего дневного распределителя
бюджета в коде — приняты, см. ниже.

## Что изменено (реализовано и стоит в продакшене)

1. **Калибровка v2** (`calibrate`): Previous Runs API, горизонты 1 и 2 суток
   раздельно, отдельные bias/std/SE **каждому семейству моделей**
   (примечание: GFS в Previous Runs живёт под именем `gfs_global`).
   Тиры: A — худшее семейство std ≤ 0.9 при n ≥ 6; B — std ≤ 1.5 при n ≥ 4;
   C — не торгуется.
2. **Вероятность v2** (`fam_prob`): равный вес каждому семейству (не по числу
   членов); каждому члену — поправка его семейства; ядро
   `τ_f² = max(0.36, std_f² − S²)`, где S² — разброс сегодняшнего ансамбля
   семейства — остаточная неопределённость без двойного счёта (ответ на
   вопрос №1). Стресс — сдвиг поправки каждого семейства на ±SE = std/√n
   (не на std: это была ошибка смешения дисперсии дня с неопределённостью
   среднего).
3. **Усадка к рынку** (вопрос №3): нормализованный лог-пул по бакетам события
   `p*_j ∝ p_j^λ · q_j^(1−λ)`, λ = 0.25 (вес модели) на фазе валидации,
   q — нормализованные середины рынка. Все решения (фильтры, EV, Келли) —
   по p*; сырая p_model сохраняется в отчёте для будущей проверки калибровки.
4. **Комиссии везде**: полная цена `c = a + 0.05·a·(1−a)` в фильтрах, EV,
   Келли, комбо, обходе стакана (`combo_lots`), обоих арбитражных детекторах
   (чистый арбитраж теперь только при сумме ПОЛНЫХ цен < 0.995; связка
   страйков — при полной цене < 0.99).
5. **Запрет дешёвых хвостов** (вопрос №9): ноги дешевле 3¢ исключены из
   комбо и одиночных входов до конца фазы валидации.
6. **Бюджет в коде** (вопрос №7): $15/день общий, **$5/день суммарно на все
   погодные входы одной даты** — считается от реальных покупок по кошельку
   (activity API), вердикты урезаются в коде, не в инструкциях.
7. **Fail-closed контроль резолюции** (вопрос №8): рынок отбрасывается, если
   единицы (°C/°F) не совпадают с моделью или источник резолюции не из
   списка Wunderground/NOAA/NWS. Отброшенные рынки перечисляются в отчёте
   (`res_checks`).
8. **Пересчёт комбо после исполнения** (вопрос №6, частично): `combo_lots`
   возвращает `ev_final` — EV набора после отсева ног и с комиссиями;
   комбо с `ev_final < 0.10` не рекомендуется.

## Принято к сведению, отложено (с причиной)

* **EMOS / оптимизация λ по log-score** — требует истории прогнозов, которая
  только начала накапливаться (система теперь пишет p_model и p* каждого
  бакета ежедневно). Вернёмся после ~2–3 недель данных.
* **Полный перебор подмножеств комбо с максимизацией log-роста** — отложен:
  при нынешних размерах ставок ($1–5) разница с жадным набором после
  пересчёта `ev_final` мала; вернёмся при росте лимитов.
* **Метрики RPS/log-loss по city-day** (вопрос №4) — план: единица
  наблюдения — city-day, не нога; Poisson-binomial тест для хвостовых
  наборов. Реализация после накопления выборки.
* **Архив разности Wunderground−METAR** (вопрос №2/№8) — Wunderground не
  отдаёт данные без ключа/скрейпинга; METAR остаётся прокси, риск признан
  и задокументирован.

## Статус после перестройки

Первый полный прогон v2: 48 городов, 0 ошибок; тиры A/B/C = 4/14/30; сигналов
дня — ноль по всем категориям, вердикты «пропуск». Это ожидаемое поведение: по
новой математике вчерашние сетапы не существовали. Пропуск дня — норма фазы
валидации.

Про внешние scheduled-задания в этом документе больше ничего не утверждается:
они живут вне репозитория, из репозитория их содержимое не проверяется, и
прошлая формулировка «оба задания обновлены и сверены побайтово» была
непроверяемым заявлением. Промпты в `docs/tasks/` — копии для чтения, а не
доказательство того, что где-то что-то обновлено.

# Закрытие блокеров безопасности v2 (2026-08-02, вторая итерация)

Ревизия v2 оставила восемь блокеров. Ниже — честный статус каждого:
что действительно сделано в коде и чем это проверяется, и что осталось
за бортом. Раздел выше описывает первую итерацию и местами ей противоречит —
приоритет у этого раздела.

## Реализовано и закрыто тестами

**1. Агрегатный бюджет.** `BudgetAllocator` ведёт ОДИН котёл на **дату
резолюции** (дата из слага рынка, `weather_date_of_slug`), а не на UTC-день
сделки. Максимумы, минимумы и серия берут деньги из одного котла: одобренная
рекомендация сразу резервирует сумму, следующая видит уменьшенный остаток.
В остаток включены уже исполненные позиции этой даты (`portfolio_scan`
группирует активность по дате погоды). Сверху действует общий дневной лимит.
Неизвестная дата — 0 (fail-closed). Тесты: `tests/test_budget.py` (12 штук).

**2. Исполнимый размер комбо.** `combo_lots` считает в `Decimal`: сначала
минимальные лоты по правилам рынка, затем отсев тонких ног, затем проверка,
что сумма минимумов влезает в `min(ставка, остаток бюджета)`, и только потом
добор до цели. `exec.total_usd` не превышает ни ставку, ни остаток. Граница
ровно в $1.00 проходит, двоичный хвост `0.9999999999999999` ногу не
отбраковывает. Минимальные лоты больше бюджета — NO BET.
Тесты: `tests/test_combo_exec.py` (9 штук).

**3. Вердикт зависит от исполнимой экономики.** `approve_combo` даёт BET
только если лоты рассчитаны, ног ≥ 2, EV после комиссий и лотов ≥ +0.10 и
сумма ≤ остатка бюджета. `plan_weather` обходит ВСЕ кандидаты одним
детерминированным проходом — ограничения «только первые шесть» больше нет;
каждый неодобренный кандидат получает явную причину, которая печатается в
отчёте. Одиночная рекомендация с ставкой ниже per-market `min_notional`
получает `stake=0` и явный `budget_block` — бюджет не тратится.
Тесты: `tests/test_verdict.py` (13 штук).

**4. Fail-closed контракт резолюции.** `parse_resolution` разбирает источник,
станцию и единицы из правил конкретного рынка; `check_resolution` не ставит
при пустых, неразбираемых, противоречивых и изменившихся правилах, при чужой
станции, при чужих или нераспознанных единицах, при нераспознанном источнике.
Живые правила Chengdu содержат UI-подсказку «To toggle between Fahrenheit and
Celsius, click the gear icon...» — `parse_resolution` фильтрует её как
display-инструкцию и возвращает `units=['C']`; `check_resolution` не даёт NO BET.
Тесты: `tests/test_resolution.py` (17 штук), включая источник, станцию,
единицы, пустые правила, валидный случай и живой Chengdu-фикстчер с UI-
подсказкой.

**5. Торговые параметры конкретного рынка.** `market_params` / `event_params`
берут ставку комиссии, тик и минимальный ордер из Gamma, при нехватке —
из CLOB по `conditionId`. Поля Gamma USDC-нотионал (`min_notional`) и CLOB
минимум в акциях (`min_shares`) хранятся РАЗДЕЛЬНО и не выводятся одно из
другого. Каноническое расписание комиссий (`feesEnabled` + `feeSchedule.rate`)
имеет приоритет над legacy `taker_base_fee`; конфликт между ними — NO BET.
`feesEnabled=False` — явный ноль (действительный). `feesEnabled=True` без
`feeSchedule` — NO BET. Нет параметров хотя бы у одного бакета или значения
вне санитарных границ — NO BET. Погода, землетрясения и крипта используют
СВОИ параметры; общей константы комиссии больше нет. `combo_lots` сравнивает
`min_total > cap` точным `Decimal` (не через `_cents`) — небольшое реальное
превышение бюджета не скрывается округлением до центов.
Тесты: `tests/test_market_params.py` (17 штук), `tests/test_combo_exec.py`
(9 штук). Сторож (`src/watchdog.py`) приведён к тем же правилам: своя копия
разбора параметров (файл запускается отдельно и импортировать соседний модуль
не может), рынок без подтверждённых параметров уходит в `param_checks` и не
торгуется, связка по страйкам засчитывается только после проверки книг.
Тесты: `tests/test_watchdog.py` (11 штук).

**6. Паритет веб-скринера.** Расчётное ядро вынесено в блок `PARITY-CORE`
внутри `web/weather_screener.html`; `tests/parity/parity_test.js` выдёргивает
его прямо из HTML и считает общие кейсы, `tests/test_parity.py` сверяет их с
Python по вероятности, усадке, комиссиям, исполнимым лотам, EV и итоговому
вердикту. Обещания «гарантированного арбитража» по `sumAsk < 0.99` убраны со
всех трёх страниц; связка считается по полным ценам с комиссиями и по книгам. Промпты в
`docs/tasks/` в этом репозитории тоже приведены к новым полям (`arb.ok`,
`exec_sets`, `param_checks`) — но это правка ТЕКСТА В РЕПОЗИТОРИИ, а не
обновление самих внешних заданий.
Тесты: `tests/test_parity.py` (13 штук, из них два — на отсутствие обещаний).

**7. Безопасность модели.** Тир и калибровка считаются ОТДЕЛЬНО для
`previous_day1` и `previous_day2`, и используется калибровка своего горизонта
(нет данных на горизонт — тир C). Лог-пул выполняется только по полному
взаимоисключающему набору исходов (`coverage_ok`); неполный набор к единице не
нормируется — событие уходит в `pool_checks`. Остаточная дисперсия вычитает
СРЕДНИЙ ИСТОРИЧЕСКИЙ разброс ансамбля окна калибровки (`hist_spread2`), а не
разброс сегодняшнего прогноза. Тесты: `tests/test_model_safety.py` (9 штук).

**8. Документация и доказательства.** `METHODOLOGY.md` переписан под текущий
код, старые формулы (Historical Forecast, общая поправка, `σ = 0.6+0.15·lead`,
стресс ±std, константа комиссии, «арбитраж = сумма асков < 0.99») вынесены в
раздел «описано исторически». `JOURNAL.md` приведён к фактически списанным
суммам: Чэнду $8.56, Шанхай $2.71, итого $11.27, сценарии — с комиссиями.
Добавлены набор тестов и GitHub Actions (`.github/workflows/tests.yml`).

## Не сделано (честно)

* **Формат полей Polymarket по комиссиям/тику/минимальному ордеру** взят из
  документации и наблюдений: `feesEnabled`/`feeSchedule.rate` (каноническое
  расписание); `taker_base_fee` (legacy, бп при значении > 1); `orderMinSize`/
  `minimum_order_size` из Gamma — USDC-нотионал; `minimum_order_size` из CLOB —
  минимум в акциях. Из этого репозитория офлайн они не проверяются. Поэтому
  любое нераспознанное, несанитарное или конфликтующее значение даёт NO BET,
  а не подстановку умолчания.
* **Внешние scheduled-задания не трогались.** Они вне репозитория; проверить
  их содержимое отсюда нельзя. Если ночной джоб продолжит запускаться старой
  копией кода, все перечисленные защиты работать не будут — обновление задачи
  остаётся ручным шагом владельца.
* **Открытые позиции не изменялись** и не будут изменены этим набором правок.
* **Wunderground как источник факта** по-прежнему недоступен без ключа; METAR
  остаётся прокси, риск задокументирован (пункт выше по документу).
* **EMOS, подбор λ по log-score, полный перебор комбо, метрики RPS/log-loss**
  остаются отложенными по прежним причинам — нужна история резолюций.
* **Contract-тесты против живого API** не добавлены: сеть в тестах запрещена
  по замыслу, все внешние вызовы замоканы. Расхождение реального формата
  Polymarket с ожидаемым тесты не поймают — его поймает fail-closed поведение
  в проде (NO BET и запись в `param_checks`).
* **Отгруженный скринер (`weather_screener.html`) не содержит калибровки lead-2.**
  Все прогнозы день-2 будут получать тир C (не торгуется), пока владелец не вставит
  актуальный JSON. Скринер может работать оффлайн, но ему нужна база калибровки.
